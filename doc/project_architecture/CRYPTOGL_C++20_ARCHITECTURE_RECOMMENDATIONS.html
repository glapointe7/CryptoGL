🏗️ 1. Project Structure & Build System Optimization (Critical Foundation)

Why This Matters for Cryptography: A well-organized project structure is crucial for cryptographic libraries because it ensures proper separation of concerns, makes security audits easier, enables better testing isolation, and provides clear boundaries between different cryptographic components. This prevents cross-contamination of security-critical code and makes the codebase more maintainable for security reviews.

1.1 Current Project Structure Analysis

Current Issues:
  • ❌ Flat Structure: All cryptographic algorithms mixed in single `src/` directory
  • ❌ No Clear Separation: Block ciphers, stream ciphers, hash functions all in same location
  • ❌ Missing Organization: No clear distinction between core utilities and algorithms
  • ❌ Build System Issues: Single CMakeLists.txt with mixed concerns
  • ❌ No Modularity: All algorithms compiled into single library
  • ❌ Missing Security Isolation: No separate security-critical components

1.3 CMakeLists.txt Optimization Strategy

Key Principles:
  • ✅ Modular Design: Each component has its own CMakeLists.txt with clear dependencies
  • ✅ Security First: All targets automatically get security hardening flags
  • ✅ Performance Optimization: SIMD detection and optimization flags applied automatically
  • ✅ Testing Integration: Comprehensive test suite with security and performance tests
  • ✅ Modern CMake: Uses target-based approach with proper dependency management

1.5 Detailed CMakeLists.txt Examples for Each Level

1.5.1 Root Level CMakeLists.txt

# File: CMakeLists.txt (Root Level) cmake_minimum_required(VERSION 3.20) project(CryptoGL VERSION 2.0 LANGUAGES CXX) # ✅ Include custom CMake modules include(cmake/CompilerFlags.cmake) include(cmake/SecurityHardening.cmake) include(cmake/PerformanceOptimization.cmake) include(cmake/Testing.cmake) # ✅ Set C++20 standard set(CMAKE_CXX_STANDARD 20) set(CMAKE_CXX_STANDARD_REQUIRED ON) set(CMAKE_CXX_EXTENSIONS OFF) # ✅ Enable modern CMake features cmake_policy(SET CMP0077 NEW) # Use absolute paths in target_sources cmake_policy(SET CMP0135 NEW) # Use absolute paths in file(GLOB) # ✅ Add subdirectories in dependency order (this creates the library targets) add_subdirectory(src/core) add_subdirectory(src/algorithms) add_subdirectory(src/big_integers) # ✅ Main executable with proper linking add_executable(${PROJECT_NAME} src/main.cpp) target_link_libraries(${PROJECT_NAME} PRIVATE cryptoGL::Core cryptoGL::Algorithms cryptoGL::BigIntegers ) # ✅ Enable testing framework enable_testing() # ✅ Add test subdirectories add_subdirectory(UnitTests) # Main test suite with 5 subdirectories add_subdirectory(tests_run) # Test runner configuration
Important: The library targets (cryptoGL::Core, cryptoGL::Algorithms, cryptoGL::BigIntegers) are created when their respective subdirectories are processed. The order matters:
  • src/core creates cryptoGL::Core and its dependencies
  • src/algorithms creates cryptoGL::Algorithms (depends on Core)
  • src/big_integers creates cryptoGL::BigIntegers
Only after all subdirectories are processed can we link against these targets.

Testing: The enable_testing() and add_subdirectory(UnitTests) ensure that the testing framework is available and test targets are built when running cmake --build . --target test.

1.5.3 UnitTests/unit/CMakeLists.txt (Unit Tests)

# File: UnitTests/unit/CMakeLists.txt # Unit tests for individual cryptographic algorithms # ✅ Helper function for creating test targets function(add_crypto_test TEST_NAME TEST_HEADER) add_executable(${TEST_NAME} ${TEST_HEADER} ${CMAKE_CURRENT_SOURCE_DIR}/../tests_run/TestsRun.cpp ) target_link_libraries(${TEST_NAME} PRIVATE cryptoGL::Core cryptoGL::Algorithms cryptoGL::BigIntegers ) # ✅ Add to CTest add_test(NAME ${TEST_NAME} COMMAND ${TEST_NAME}) # ✅ Apply security flags apply_crypto_security_flags(${TEST_NAME}) endfunction() # ✅ Automatic test discovery for algorithm tests # Only include files that end with "Test.hpp" to avoid utility headers file(GLOB TEST_HEADERS "*Test.hpp") foreach(HEADER ${TEST_HEADERS}) get_filename_component(TEST_NAME ${HEADER} NAME_WE) # Remove "Test" suffix to get clean test name (e.g., "AESTest" -> "test_aes") string(REPLACE "Test" "" CLEAN_NAME ${TEST_NAME}) string(TOLOWER ${CLEAN_NAME} CLEAN_NAME_LOWER) add_crypto_test(test_${CLEAN_NAME_LOWER} ${HEADER}) # Store test names for later use in set_tests_properties list(APPEND ALL_UNIT_TESTS test_${CLEAN_NAME_LOWER}) endforeach() # Alternative: Manual addition for specific tests if needed # add_crypto_test(test_custom CustomTest.hpp) # list(APPEND ALL_UNIT_TESTS test_custom) # ✅ Set test properties for all discovered unit tests set_tests_properties(${ALL_UNIT_TESTS} PROPERTIES TIMEOUT 60 LABELS "unit" ) # ✅ Debug: Print discovered tests (optional, remove in production) message(STATUS "Discovered unit tests: ${ALL_UNIT_TESTS}")
Automatic Test Discovery Benefits:
  • Maintainable: No need to manually add new tests - just create a new *Test.hpp file
  • Consistent: All tests follow the same naming pattern and configuration
  • Scalable: Easy to add new algorithm tests without touching CMakeLists.txt
  • Less Error-Prone: No forgotten test additions or typos
Important Considerations:
  • File Naming: Tests must follow the "*Test.hpp" pattern
  • CMake Cache: Run cmake --fresh if new tests aren't detected
  • Debug Output: The message(STATUS ...) shows discovered tests during configuration
  • Fallback: You can still manually add specific tests if needed
Running Individual Tests:
  • By Name: ctest -R test_aes (runs only AES test)
  • By Label: ctest -L unit (runs only unit tests)
  • By Pattern: ctest -R ".*aes.*" (runs any test containing "aes")
  • By Number: ctest -I 5 (runs test number 5)
  • List Tests: ctest -N (shows all tests with numbers)
