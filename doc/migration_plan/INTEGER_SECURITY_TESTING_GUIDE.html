🎯 1. Introduction to Cryptographic Security Testing

Security testing for cryptographic libraries goes beyond functional correctness to verify that implementations resist various attack vectors. For integer operations in cryptographic contexts, security testing focuses on preventing information leakage through timing, power consumption, electromagnetic emissions, and memory access patterns.

⚠️ Critical Security Principle:

In cryptographic implementations, how an operation executes is as important as what it computes. Side-channel attacks can extract secret information from implementation details that seem innocuous.

🔍 Security Testing Objectives

  • Constant-Time Verification: Ensure execution time is independent of secret data
  • Memory Access Pattern Analysis: Verify uniform memory access regardless of input
  • Cache-Timing Resistance: Prevent cache-based side-channel attacks
  • Branch Pattern Analysis: Ensure predictable control flow
  • Input Validation: Robust handling of malicious or malformed inputs
  • Memory Safety: Prevent buffer overflows and information disclosure

🎯 2. Threat Model & Attack Vectors

🚨 Primary Attack Vectors Against Integer Operations

1. Timing Attacks

Attackers measure execution time variations to infer information about secret data processed by integer operations.

2. Cache-Timing Attacks

Exploiting CPU cache behavior differences based on memory access patterns during computation.

3. Branch Prediction Attacks

Analyzing CPU branch predictor state to infer secret-dependent conditional operations.

4. Power Analysis Attacks

Measuring power consumption during operations to extract information about processed data.

5. Electromagnetic Analysis

Monitoring electromagnetic emissions from computing devices during cryptographic operations.

6. Fault Injection Attacks

Introducing controlled faults (voltage glitches, clock manipulation) to cause computational errors.

🛡️ Defense Mechanisms

Constant-Time Programming

Ensuring execution time and resource usage are independent of secret values.

Memory Access Uniformity

Maintaining consistent memory access patterns regardless of input data.

Branch Elimination

Using branchless implementations to avoid secret-dependent control flow.

Input Sanitization

Comprehensive validation and normalization of all inputs.

  • Measurement: Statistical analysis over 10,000+ samples

  • Requirement: Consistent memory access patterns
  • Measurement: Cache miss rate analysis
  • Tolerance: Cache behavior independent of secret data

  • Requirement: No secret-dependent branches
  • Measurement: Branch predictor analysis
  • Implementation: Branchless algorithms preferred

  • Requirement: Robust handling of all input ranges

⏱️ 5. Timing Attack Resistance Testing

🎯 Mathematical Foundation of Timing Attacks

📚 Theory: How Timing Attacks Work

Timing attacks exploit the fact that cryptographic operations may take different amounts of time depending on the secret data being processed. An attacker measures these timing differences to infer information about secret keys or internal state.

Mathematical Model:

Let T(x, k) be the execution time of an operation with input x and secret k. A timing attack exists if:

Mathematical Condition for Timing Attack Vulnerability: ∃ k₁, k₂, x : |T(x, k₁) - T(x, k₂)| > δ Where: - k₁, k₂ are different secret values - x is a chosen input - δ is the measurement precision threshold - T(x, k) is the execution time function If this condition holds, an attacker can distinguish between k₁ and k₂.

🔍 Concrete Example: LSB Extraction Timing Attack

Consider the Integer.hpp LSB extraction function:

// Potentially vulnerable implementation (example) uint32_t extract_lsb_vulnerable(uint32_t value, uint8_t bits) { uint32_t result = 0; for (uint8_t i = 0; i < bits; ++i) { // Loop count depends on 'bits' if (value & (1U << i)) { // Branch depends on bit value result |= (1U << i); } } return result; } // Attack scenario: // - Attacker controls 'bits' parameter (public) // - 'value' contains secret data // - Execution time varies with: // 1. Number of bits to extract (loop iterations) // 2. Number of set bits (branch predictions)
Timing Attack Example:
Attack Methodology: 1. Measure T₁ = time for extract_lsb(secret_value, 1) 2. Measure T₂ = time for extract_lsb(secret_value, 2) 3. Measure T₃ = time for extract_lsb(secret_value, 3) ... Analysis: - If T₂ - T₁ > threshold: bit 1 is likely set (extra branch taken) - If T₃ - T₂ > threshold: bit 2 is likely set - Statistical analysis over many measurements reveals bit pattern Mathematical Recovery: secret_bit_i = 1 if (T_{i+1} - T_i) > μ + 2σ = 0 otherwise Where μ is mean timing difference, σ is standard deviation

🎯 Constant-Time Verification Methodology

Statistical Timing Analysis

We use multiple statistical tests to verify timing independence from secret data:

1. Analysis of Variance (ANOVA)
ANOVA Test for Timing Uniformity: H₀ (Null Hypothesis): μ₁ = μ₂ = ... = μₖ (all group means equal) H₁ (Alternative): At least one μᵢ ≠ μⱼ (timing depends on secret data) F-statistic = MSB / MSW Where: MSB = Σnᵢ(x̄ᵢ - x̄)² / (k-1) (Mean Square Between groups) MSW = ΣΣ(xᵢⱼ - x̄ᵢ)² / (N-k) (Mean Square Within groups) k = number of groups (different secret values) N = total number of measurements nᵢ = number of measurements in group i x̄ᵢ = mean timing for group i x̄ = overall mean timing Decision Rule: - If F > F_{critical}(α, k-1, N-k): Reject H₀ (VULNERABLE) - If F ≤ F_{critical}: Accept H₀ (SECURE) Example with Integer::lsb(): Group 1: Extract 1 bit → timings = [12.3, 12.1, 12.4, 12.2] ns Group 2: Extract 8 bits → timings = [15.1, 15.3, 15.0, 15.2] ns Group 3: Extract 16 bits→ timings = [18.7, 18.9, 18.6, 18.8] ns F = 2847.6, F_critical(0.05, 2, 9) = 4.26 Since F > F_critical: VULNERABLE (timing depends on bit count)
2. Welch's T-Test for Unequal Variances
Welch's T-Test Mathematical Formula: t = (x̄₁ - x̄₂) / √(s₁²/n₁ + s₂²/n₂) Degrees of freedom (Welch-Satterthwaite equation): ν = (s₁²/n₁ + s₂²/n₂)² / [(s₁²/n₁)²/(n₁-1) + (s₂²/n₂)²/(n₂-1)] Where: x̄₁, x̄₂ = sample means for two groups s₁², s₂² = sample variances n₁, n₂ = sample sizes Example Application: Test if timing for rotateLeft(value, 1) equals rotateLeft(value, 31) Group 1 (shift=1): mean=10.2ns, variance=0.15, n=1000 Group 2 (shift=31): mean=10.8ns, variance=0.22, n=1000 t = (10.2 - 10.8) / √(0.15/1000 + 0.22/1000) = -31.2 ν = 1945.3 p-value = P(|t| > 31.2) ≈ 0 (highly significant) Conclusion: VULNERABLE (timing depends on shift amount)
3. Pearson Correlation Analysis
Correlation Between Input Values and Timing: r = Σ(xᵢ - x̄)(yᵢ - ȳ) / √[Σ(xᵢ - x̄)²Σ(yᵢ - ȳ)²] Where: xᵢ = input values (e.g., rotation amount) yᵢ = corresponding timing measurements x̄, ȳ = means of x and y Interpretation: |r| < 0.1: No correlation (SECURE) 0.1 ≤ |r| < 0.3: Weak correlation (MONITOR) 0.3 ≤ |r| < 0.7: Moderate correlation (VULNERABLE) |r| ≥ 0.7: Strong correlation (CRITICAL) Example with bytesSwap(): Input values: [0x12345678, 0x87654321, 0xAAAABBBB, 0x11111111] Timings: [8.2, 8.1, 8.9, 7.8] ns r = -0.23 (weak negative correlation) Verdict: MONITOR (potential timing dependency)

// Sort for median calculation auto sorted_timings = timings; std::sort(sorted_timings.begin(), sorted_timings.end()); stats.sample_count = timings.size(); stats.min_time = sorted_timings.front(); stats.max_time = sorted_timings.back(); } else { stats.median = sorted_timings[mid]; } // Calculate standard deviation double variance = 0.0; for (const auto& time : timings) { variance += std::pow(time - stats.mean, 2); } stats.std_deviation = std::sqrt(variance / stats.sample_count); double grand_mean = 0.0; // Calculate grand mean for (const auto& group : groups) { total_samples += group.size(); grand_mean += std::accumulate(group.begin(), group.end(), 0.0); } grand_mean /= total_samples; // Calculate between-group and within-group sum of squares double ss_between = 0.0; double ss_within = 0.0; for (const auto& group : groups) { double group_mean = std::accumulate(group.begin(), group.end(), 0.0) / group.size(); ss_between += group.size() * std::pow(group_mean - grand_mean, 2); for (const auto& value : group) { ss_within += std::pow(value - group_mean, 2); } } // Calculate F-statistic size_t df_between = groups.size() - 1; size_t df_within = total_samples - groups.size(); double ms_between = ss_between / df_between; double ms_within = ss_within / df_within; return ms_between / ms_within; } bool performWelchTTest(const std::vector<std::vector<double>>& groups) { // Implementation of Welch's t-test for unequal variances // Returns true if groups are statistically similar (p > 0.05) if (groups.size() < 2) return true; // Compare first group with all others const auto& baseline = groups[0]; for (size_t i = 1; i < groups.size(); ++i) { const auto& comparison = groups[i]; double t_statistic = calculateWelchTStatistic(baseline, comparison); double p_value = calculateTTestPValue(t_statistic, baseline.size(), comparison.size()); if (p_value < 0.05) { return false; // Significant difference detected } } return true; } double calculateWelchTStatistic(const std::vector<double>& group1, const std::vector<double>& group2) { auto stats1 = calculateTimingStatistics(group1); auto stats2 = calculateTimingStatistics(group2); double variance1 = std::pow(stats1.std_deviation, 2); double variance2 = std::pow(stats2.std_deviation, 2); double pooled_se = std::sqrt((variance1 / group1.size()) + (variance2 / group2.size())); return (stats1.mean - stats2.mean) / pooled_se; } };

📡 6. Side-Channel Attack Testing

🔍 Mathematical Foundation of Cache-Timing Attacks

📚 Theory: How Cache-Timing Attacks Work

Cache-timing attacks exploit the difference in access time between cache hits and cache misses. When an operation accesses memory, the pattern of which memory locations are accessed can leak information about secret data through observable timing differences.

Mathematical Model:
Cache Access Time Model: T_access = T_hit × P(hit) + T_miss × P(miss) Where: - T_hit ≈ 1-4 CPU cycles (cache hit time) - T_miss ≈ 100-300 CPU cycles (main memory access time) - P(hit) = probability of cache hit - P(miss) = 1 - P(hit) Cache Attack Condition: If P(hit) depends on secret data s, then: ∃ s₁, s₂ : |P(hit|s₁) - P(hit|s₂)| > ε Where ε is the detection threshold.

🔍 Concrete Example: Bit Position Cache Attack

Consider accessing bits at different positions in Integer operations:

// Potentially vulnerable memory access pattern bool getBitAtPosition_vulnerable(uint32_t value, uint8_t position) { // Different positions may map to different cache lines static const uint32_t lookup_table[32] = { 0x00000001, 0x00000002, 0x00000004, 0x00000008, 0x00000010, 0x00000020, 0x00000040, 0x00000080, // ... 32 entries, each potentially in different cache lines }; return (value & lookup_table[position]) != 0; // Cache-dependent access } Cache Attack Scenario: 1. Attacker measures cache state before operation 2. Target executes getBitAtPosition(secret_value, secret_position) 3. Attacker probes cache to see which lines were accessed 4. Cache access pattern reveals information about secret_position
Prime-and-Probe Attack Mathematical Analysis:
Prime-and-Probe Attack Steps: 1. PRIME: Fill cache with attacker's data for i in cache_lines: access(attacker_data[i]) // Fills cache line i 2. WAIT: Victim executes secret-dependent operation victim_operation(secret_data) 3. PROBE: Measure access time to each cache line for i in cache_lines: time[i] = measure_access_time(attacker_data[i]) Analysis: - If time[i] > threshold: cache line i was evicted (victim accessed it) - If time[i] ≤ threshold: cache line i still cached (victim didn't access) Mathematical Recovery: accessed_lines = {i : time[i] > μ + 2σ} Where μ is mean probe time, σ is standard deviation Example with Integer::getByteAtPosition(): Byte position 0: affects cache lines {0, 1} Byte position 1: affects cache lines {1, 2} Byte position 2: affects cache lines {2, 3} ... Attack Result: accessed_lines = {1, 2} → secret byte position = 1

Cache Uniformity Statistical Analysis

1. Cache Miss Rate Analysis
Cache Uniformity Test: Let M_i = cache miss rate for operation with parameter i Uniformity Hypothesis: H₀: M₁ = M₂ = ... = M_k (uniform cache behavior) H₁: ∃ i,j : M_i ≠ M_j (cache behavior depends on secret data) Chi-Square Test for Cache Uniformity: χ² = Σ(O_i - E_i)² / E_i Where: O_i = observed cache misses for parameter i E_i = expected cache misses (uniform distribution) Decision Rule: - If χ² > χ²_critical(α, k-1): VULNERABLE - If χ² ≤ χ²_critical: SECURE Example with Integer::rotateLeft(): shift=1: cache_misses = 150, expected = 120 shift=8: cache_misses = 89, expected = 120 shift=16: cache_misses = 201, expected = 120 χ² = (150-120)²/120 + (89-120)²/120 + (201-120)²/120 = 69.2 χ²_critical(0.05, 2) = 5.99 Since χ² > χ²_critical: VULNERABLE (cache behavior varies by shift)
2. Cache Line Correlation Analysis
Cache Line Access Correlation: Correlation between secret value and cache line access pattern: r_line = Σ(s_i - s̄)(c_i - c̄) / √[Σ(s_i - s̄)²Σ(c_i - c̄)²] Where: s_i = secret input values c_i = number of cache lines accessed for input s_i s̄, c̄ = means of secret values and cache accesses Cache Security Threshold: |r_line| < 0.1: SECURE (no correlation) |r_line| ≥ 0.1: VULNERABLE (secret leaks through cache) Example with Integer::bytesSwap(): Secret values: [0x12345678, 0x87654321, 0xAAAAAAAA, 0x55555555] Cache lines: [3, 4, 2, 3] (accessed during operation) r_line = 0.34 (moderate positive correlation) Verdict: VULNERABLE (cache pattern reveals input information)

🌿 6.5 Branch Prediction Attack Theory

📚 Theory: How Branch Prediction Attacks Work

Branch prediction attacks exploit the CPU's branch predictor state to infer information about secret data. When code contains secret-dependent conditional branches, the pattern of taken/not-taken branches can leak information through timing differences caused by mispredictions.

Mathematical Model:
Branch Prediction Model: T_branch = T_predicted × P(correct) + T_mispredicted × P(mispredict) Where: - T_predicted ≈ 1 CPU cycle (correctly predicted branch) - T_mispredicted ≈ 10-20 CPU cycles (pipeline flush penalty) - P(correct) = probability of correct branch prediction - P(mispredict) = 1 - P(correct) Branch Attack Condition: If P(correct) depends on secret data s, then: ∃ s₁, s₂ : |P(correct|s₁) - P(correct|s₂)| > ε Attack succeeds when secret data affects branch prediction accuracy.

🔍 Concrete Example: Secret-Dependent Branch Attack

Branch Prediction State Attack:

Branch Entropy Analysis

Branch Entropy Calculation: For a sequence of branch outcomes B = {b₁, b₂, ..., bₙ} where bᵢ ∈ {0,1}: H(B) = -Σ P(bᵢ) log₂ P(bᵢ) Where P(bᵢ) is the probability of branch outcome bᵢ. 🔒 6.6 Input Validation Security Theory

📚 Theory: Input Validation Vulnerabilities

Input validation vulnerabilities occur when cryptographic implementations don't properly handle edge cases, boundary conditions, or malicious inputs. These can lead to crashes, undefined behavior, or information disclosure.

Mathematical Model:
Input Domain Analysis: Let D = valid input domain for function f Let I = all possible inputs (including invalid) Vulnerability exists if: ∃ x ∈ (I \ D) : f(x) reveals information about internal state Security Requirements: 1. Completeness: ∀ x ∈ D, f(x) is well-defined 2. Soundness: ∀ x ∈ (I \ D), f(x) fails securely 3. Consistency: timing(f(x)) independent of x for x ∈ D

🔍 Concrete Example: Boundary Condition Attack

⚡ 6.7 Fault Injection Attack Theory

📚 Theory: How Fault Injection Attacks Work

Fault injection attacks introduce controlled errors during computation to cause the system to produce incorrect results that reveal secret information. Common fault types include bit flips, instruction skips, and timing glitches.

Mathematical Model:
Fault Model: Let f(x) = correct computation result Let f'(x) = result under fault injection Fault Attack Success Condition: ∃ fault F : analysis(f(x), f'(x)) reveals secret information Common Fault Types: 1. Bit flip: f'(x) = f(x ⊕ 2^i) for some bit position i 2. Instruction skip: f'(x) = f_partial(x) (incomplete execution) 3. Variable corruption: f'(x) = f(x') where x' = x + δ Fault Differential Analysis: Δ = f(x) ⊕ f'(x) (difference between correct and faulty output) If Δ has exploitable structure → attack succeeds

🔍 Concrete Example: Bit Flip Fault Attack

// Target function for fault injection uint32_t secureRotation(uint32_t secret_key, uint8_t rounds) { uint32_t result = secret_key; for (uint8_t i = 0; i < rounds; ++i) { result = rotateLeft(result, 1); result ^= ROUND_CONSTANT[i]; } return result; } Fault Injection Attack: 1. Statistical Fault Analysis:

Fault Detection Rate: FDR = (detected_faults / total_faults) × 100% Target: FDR > 95% 2.   • ✅ Good: Consistent cache behavior across all inputs (<5% miss rate variation)

  • ✅ Good: All valid inputs work, all invalid inputs fail gracefully
