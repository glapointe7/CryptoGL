1. 🎯 Overview and Objectives

Primary Goal

Transform the current dynamic Vector<T>-based BlockCipher architecture to use compile-time fixed-size Array<T, Size> for:

  • Compile-time optimization - All block sizes known at compile time
  • Constant-time execution - Elimination of timing side-channels
  • Zero-cost abstraction - No runtime overhead
  • Enhanced security - Predictable memory access patterns

🚀 Key Benefits of Array.hpp Integration

  • Compile-time guarantees: Block sizes validated at compile time
  • Constant-time operations: Built-in timing-resistant operations
  • Memory efficiency: Stack allocation instead of heap
  • Optimizer-friendly: Better loop unrolling and vectorization

3. 🔧 Array.hpp Integration Strategy

New Template Architecture

Key Insight: Leveraging Template Parameter Deduction

Since you already have typename InputBlockType and uint8_t InputBlockSize, we can derive the Array element type and size automatically:

  • InputBlockType = Array<ElementType, BlockElementCount>
  • InputBlockSize = total bytes (unchanged)
  • ElementType = extracted from InputBlockType
  • BlockElementCount = InputBlockSize / sizeof(ElementType)

Proposed New Architecture

Proposed: New Array-based BlockCipher
// New architecture leveraging Array.hpp
template <typename SubkeyType,
          typename InputBlockType,
          uint8_t InputBlockSize,
          typename EndianType>
class BlockCipherArray : public SymmetricCipher<BytesVector>
{
    static_assert(is_array_type_v<InputBlockType>,
                  "InputBlockType must be Array<T, N>");
    static_assert(InputBlockType::size() * sizeof(typename InputBlockType::value_type) == InputBlockSize,
                  "Array size must match InputBlockSize");

    using ElementType = typename InputBlockType::value_type;
    static constexpr size_t BlockElementCount = InputBlockType::size();
    
    InputBlockType current_block; // Now Array<ElementType, BlockElementCount>
};

7. 🤔 Why These Changes? Before vs After Analysis

Core Problem with Current Approach

Your current BlockCipher uses dynamic Vector<T> which causes:

  • Runtime overhead: Heap allocation, bounds checking, indirect access
  • Timing vulnerabilities: Variable memory access patterns
  • No compile-time guarantees: Block sizes validated at runtime
  • Missed optimizations: Compiler can't unroll loops or vectorize effectively
